# 기존 행성 점검 및 재분석

2026-11-26 확인: 운영 `https://api.star2day.com/openapi.json`의 `GroupStarEntry`에는 `topic` 속성이 없었습니다. 로컬/원격 test의 스키마에는 이미 있습니다. 현재 운영 서버 배포 버전이 다르므로 프론트 배포만으로 그룹 주제 집계 0개를 해결할 수 없습니다.

## 먼저 배포하기

1. test의 변경을 검토하고 GitHub에 반영합니다.
2. Cloudtype에서 `api.star2day.com`이 연결된 **기존 백엔드 서비스**를 엽니다. `group-push-worker`나 새 서비스가 아닙니다.
3. 설정의 Git 브랜치가 `test`, 서브 디렉터리가 `backend`인지 확인하고 최신 test로 재배포합니다. 기존 환경변수와 시작 명령은 유지합니다.
4. 배포 후 아래 명령은 **컴퓨터 PowerShell**에서 실행합니다. `True`가 나와야 주제 응답을 지원하는 백엔드입니다. 실패하면 프론트 집계를 임의로 바꾸지 말고 배포 커밋과 API 도메인 연결을 확인합니다.

```powershell
$schema = Invoke-RestMethod 'https://api.star2day.com/openapi.json'
$null -ne $schema.components.schemas.GroupStarEntry.properties.topic
```

5. 웹에서 새로고침 → 그룹 진입 → 별자리 보기 → 주제 다시 불러오기로 확인합니다. `topic: null`인 과거 일기는 여전히 제외되며, 실제 선택 주제나 기존 AI 주제 저장소에 근거 없는 분류를 만들지 않습니다.

## 예전 행성이 회색인 경우

- 모델 도입 전 글도 `/stars`와 그룹 별 목록을 읽을 때 현재 AI로 외형을 계산합니다. 작성 날짜로 제외하지 않습니다.
- `planet` 응답이 없으면 프론트는 무늬 없는 기본 행성을 그립니다. AI 연결/시간 초과와 감정 판정 없음(`none`/`muted`)은 서로 다릅니다.
- 조회 실패한 결과는 캐시하지 않으며 다음 조회에서 재시도합니다. 한 묶음 실패 때문에 다른 정상 결과까지 버리지 않습니다.
- 모델을 교체했다면 백엔드를 재시작해 이전 프로세스의 외형 캐시를 비웁니다. 최신 배포도 이 효과가 있습니다.

## 실제 데이터 전체 확인

아래 명령은 **Cloudtype의 기존 백엔드 서비스 터미널**에서 실행합니다. 프로젝트의 기존 환경변수를 사용하므로 키를 명령어에 넣거나 채팅에 붙이지 않습니다. `scripts/reanalyze_planets.py`가 있는 backend 디렉터리 기준입니다.

먼저 테스트 문장만 확인합니다. DB를 읽거나 수정하지 않습니다. ‘테스트’의 판정 결과는 실제 모델 실행 전에는 단정할 수 없습니다.

```sh
python scripts/reanalyze_planets.py --sample-text "테스트"
```

기존 행성 **전체**를 현재 모델로 점검합니다. 이 명령은 기본적으로 DB를 수정하지 않으며 일기 내용이나 계정 정보도 출력하지 않습니다. AI 계산은 기존에 설정된 서비스에서 수행됩니다.

```sh
python scripts/reanalyze_planets.py
```

결과 의미: `total` 전체 / `clear` 뚜렷한 감정 / `soft` 약한 감정 / `muted` 판정 불확실 / `none` 감정 없음 우세 / `changed` 저장된 색·밝기와 다른 결과 / `failed` 분석 실패 / `empty` 빈 내용.

전체 결과를 확인한 뒤 기존 저장 색·밝기도 현재 판정으로 갱신하려면:

```sh
python scripts/reanalyze_planets.py --apply
```

`--apply`는 모든 계정의 기존 행성에 적용합니다. 특정 계정만 점검/적용하려면 `--user-id 계정UUID`를 추가합니다. 좌표·일기·공유 대상·주제·장착 효과·표면 아이템은 바꾸지 않습니다. 실패한 분석으로 기존 값을 덮어쓰지 않습니다. 정상적으로 감정이 없거나 불확실한 글은 회색일 수 있습니다.

`failed`가 있다면 AI 서비스 상태와 로그를 확인합니다. 처리 시간이 긴 환경에서는 `--batch-size 1 --timeout 120`으로 다시 점검할 수 있습니다. `write_failed`가 있다면 DB 권한/연결을 확인합니다. 전체 실패·부분 실패 시 명령은 종료 코드 1을 반환하며 성공한 갱신은 유지됩니다.

적용 후 기존 백엔드 서비스를 다시 시작하고 웹을 새로고침합니다. `updated`는 갱신 성공 개수이며, 외형의 무늬/고리는 조회 시 AI 응답으로 계산됩니다. 무조건 유색 행성으로 만들거나 감정을 임의 배정하지 않습니다.

이 문서 작성 시 운영 DB 전체 점검과 `--apply`는 실행하지 않았습니다.
