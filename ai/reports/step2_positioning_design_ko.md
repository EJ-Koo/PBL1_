# 2단계 설계: 의미 임베딩 → 행성 위치·군집·별자리

- 프로젝트: 오늘의별일 · 작성일: 2026-10-26 · 상태: **설계안** (2026-10-27: 의미 임베딩·관련 기억·좌표는 구현됨 → `step2_local_validation_ko.md`, `step2_integration_local_ko.md`. 군집·별자리·이름 붙이기는 미구현)
- 전제: 1단계 완료. 일기를 저장하면 AI 서비스가 감정을 분석해 별 색·밝기를 정한다(`ai/service`, `backend/app/ai_client.py`).
- 이 단계의 목표: 지금 **무작위**인 별 위치(x, y, z)를 **일기 의미에 따라** 정한다. 비슷한 기억은 가까이 모이고(군집), 관련 기억은 선(별자리)으로 잇는다.

## 1. 현재 상태와 바꿀 점

| 항목 | 현재 | 2단계 후 |
|---|---|---|
| 위치 x, y, z | 반지름 3~12의 구 껍질 위 무작위 (`backend/app/routers/diaries.py`) | 일기 의미 임베딩 기반 3D 좌표 |
| 군집 | 없음 | 사용자별 의미 군집(HDBSCAN). 같은 군집은 우주의 한 영역에 모임 |
| 별자리 | 없음 | 의미가 가까운 일기끼리 연결선 |
| 관련 기억 검색 | 없음 | 임베딩 유사도 상위 k개 |
| 그룹 우주 | 개인 우주 좌표를 그대로 사용 | 그룹 일기만으로 따로 배치(선택) |

DB 스키마 주석에 이미 "HDBSCAN 클러스터링 결과 → x/y/z 좌표"로 정해져 있다. 이 설계는 그 방향을 따른다.

## 2. 처리 흐름

```
일기 저장
  └ 백엔드 ─▶ AI 서비스 POST /analyze  (1단계: 감정 → 색·밝기)
           ─▶ AI 서비스 POST /embed    (2단계: 텍스트 → 의미 벡터)  ─▶ DB 저장 (pgvector)
           ─▶ AI 서비스 POST /layout   (사용자의 전체 벡터 → 좌표·군집·별자리)
                └ stars.x/y/z, cluster_id 갱신 + 별자리 연결선 저장
앱 ─▶ GET /stars (좌표·군집), GET /constellations (연결선), GET /diaries/{id}/related (관련 기억)
```

## 3. 구성 요소별 설계

### 3.1 의미 임베딩 모델

| 후보 | 크기 | 라이선스 | 특징 |
|---|---|---|---|
| `nlpai-lab/KURE-v1` | 568M | MIT | BGE-M3를 한국어 검색용으로 추가 학습(고려대). 1순위 후보 |
| `BAAI/bge-m3` | 568M | MIT | 다국어 검색 모델. 원래 계획의 모델 |
| `intfloat/multilingual-e5-small` | 118M | MIT | 가벼운 대안. CPU 서버에서 빠름 |

- **선택 방법**: 아래 5절의 평가(가상 일기 주제 군집 정확도, 관련 기억 검색 정확도, CPU 속도)로 고른다. 벤치마크 점수만으로 정하지 않는다. 감정 모델에서도 벤치마크 점수가 높았던 A.X가 실제 과제에서는 낮았다.
- 일기 원문을 외부 API로 보내지 않도록 AI 서비스 안에서 로컬로 실행한다.

### 3.2 저장 (Supabase, 팀 협의 필요)

```sql
create extension if not exists vector;
create table diary_embeddings (
  diary_id uuid primary key references diaries (id) on delete cascade,
  model text not null,                 -- 모델 이름·버전 (모델을 바꾸면 다시 계산)
  embedding vector(1024) not null,     -- KURE/BGE-M3 기준 1024차원
  created_at timestamptz not null default now()
);
alter table stars add column cluster_id integer;           -- -1: 군집 없음(외톨이 별)
create table constellation_edges (
  user_id uuid not null, a uuid not null references diaries(id) on delete cascade,
  b uuid not null references diaries(id) on delete cascade, weight real not null,
  primary key (user_id, a, b)
);
```
- RLS는 기존 `stars`처럼 `diaries.user_id = auth.uid()`로 소유권을 확인한다. 임베딩은 원문에서 만든 민감 정보로 다룬다.
- 일기를 지우면 임베딩과 연결선도 함께 지워진다(`on delete cascade`).

### 3.3 군집 (HDBSCAN)

- 사용자별로 그 사용자 일기의 임베딩만 묶는다(코사인 거리). scikit-learn 1.3 이상의 `HDBSCAN`을 쓰면 별도 라이브러리가 필요 없다.
- 일기 수가 적은 초기 사용자(예: 8개 미만)는 군집을 만들지 않는다. 군집에 들지 않는 일기(노이즈)는 ‘외톨이 별’로 둔다.
- `min_cluster_size`는 평가로 정한다(초기값 3).

### 3.4 3D 좌표 (가장 중요한 결정)

일기가 하나 추가될 때마다 **기존 별들이 크게 움직이면 안 된다**(사용자에게 ‘내 우주’가 매번 바뀌어 보임). 그래서 품질과 안정성을 함께 평가해 고른다.

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 고정 투영 | 참조 문장 집합으로 임베딩 → 3D 투영(PCA)을 한 번 정해 두고 모든 일기에 같은 식 적용 | 새 일기를 넣어도 **기존 별이 전혀 안 움직임**, 단순·빠름 | 3차원에 담기는 정보가 적어 이웃 관계 보존이 약할 수 있음 |
| B. 사용자별 재배치 | 사용자의 전체 임베딩으로 매번 UMAP 3D 배치 | 이웃 관계 보존이 가장 좋음 | 매번 전체가 바뀜. 이전 배치에 정렬(Procrustes)해도 움직임이 남음 |
| **C. 군집 앵커 + 점진 배치 (권장안)** | 군집 중심을 구 위에 고정 배치. 새 일기는 가장 가까운 이웃 별들 근처에 놓음. 일기가 많이 쌓이면 가끔 전체를 재배치하고 이전 배치에 정렬 | 의미 군집이 우주의 ‘영역’으로 보이고, 평소에는 기존 별이 안 움직임 | 구현이 가장 복잡함 |

- 반지름(중심 거리)은 지금처럼 3~12 범위를 유지해 프론트 카메라·회전과 맞춘다.
- **선택지**: 위치에 감정을 함께 반영할 수 있다(예: 높이(y) = 정서, 위쪽이 긍정). 의미와 감정 중 무엇을 위치로 표현할지는 기획 결정이 필요하다. 기본안은 위치 = 의미, 색 = 감정(1단계)이다.

### 3.5 별자리 (연결선)

- 같은 군집 안에서 유사도가 기준 이상인 일기끼리 잇되, 선이 너무 많아지지 않도록 군집별 최소 신장 트리(MST)를 쓴다.
- 기준 유사도는 평가로 정한다.
- 프론트에는 연결선 표시 기능이 필요하다. 3D 선을 추가하는 것이라 디자인 요소이므로 형태는 프론트와 협의한다.

### 3.6 관련 기억 검색

- `GET /diaries/{id}/related?k=5`: pgvector 코사인 유사도 상위 k개(본인 일기만)

### 3.7 그룹 우주

- 기본안: 지금처럼 개인 좌표를 그대로 쓴다(변경 없음).
- 선택안: 그룹 일기만으로 3.3~3.5를 따로 계산해 그룹 전용 좌표를 둔다(테이블 1개 추가). 그룹원이 많아지면 의미 있는 선택이다.

## 4. AI 서비스 API (추가 예정)

| API | 입력 | 출력 |
|---|---|---|
| `POST /embed` | `{"texts": [...]}` | `{"model", "embeddings": [[...1024]]}` |
| `POST /layout` | `{"items": [{"diary_id", "embedding", "prev_xyz"?}]}` | `{"stars": [{"diary_id", "x", "y", "z", "cluster_id"}], "edges": [{"a", "b", "weight"}]}` |

백엔드는 1단계처럼 실패해도 일기 저장이 되도록 한다(실패하면 지금의 무작위 배치 유지).

## 5. 검증 계획 (구현 전에 먼저 실행)

실제 일기 데이터가 없으므로 **가상 일기 세트**(개발자 작성, 주제 8~10개 × 주제당 6~8개, 약 60~80개)를 만들어 평가한다. 예: 시험·과제, 가족, 연애, 친구, 운동, 여행, 아르바이트·일, 건강, 취미.

| 평가 | 지표 | 목적 |
|---|---|---|
| 임베딩 모델 비교 | 주제 군집 일치도(ARI), 같은 주제 검색 정확도(top-5), CPU 속도 | 3.1 모델 선택 |
| 군집 설정 | HDBSCAN `min_cluster_size`별 ARI·외톨이 비율 | 3.3 설정값 |
| 좌표 방식 비교 | 이웃 보존(trustworthiness, kNN 보존율), 군집 분리 | 3.4 방식 선택 |
| 안정성 | 일기를 하나씩 추가할 때 기존 별의 평균 이동 거리 | 3.4 방식 선택 |
| 별자리 | 연결선이 같은 주제를 잇는 비율 | 3.5 기준값 |

결과는 `ai/notebooks/07_embedding_layout.ipynb`(예정)에 정리하고, 3D 미리보기 그림으로 확인한다.

## 6. 진행 순서 (제안)

1. 가상 일기 세트 작성 → 임베딩 모델 3종 비교 → 모델 선택
2. 군집·좌표 방식(A/B/C) 비교 → 방식 선택 (오프라인, 노트북)
3. AI 서비스에 `/embed`, `/layout` 추가 + 테스트
4. DB 스키마 추가(팀 협의) → 백엔드 연동(일기 저장 시 좌표 갱신) + 테스트
5. 기존 일기 일괄 계산 스크립트(백필)
6. 프론트: 서버 좌표는 이미 사용 중이므로 그대로 동작. 별자리 선 표시만 추가(디자인 협의)

## 7. 결정이 필요한 사항

1. 위치에 무엇을 표현할지: **의미만**(기본안) / 의미 + 정서(예: 높이)
2. 좌표 방식: 평가 후 결정하되, 안정성(기존 별이 안 움직임)을 얼마나 중요하게 볼지
3. DB 스키마 추가(pgvector, `diary_embeddings`, `stars.cluster_id`, `constellation_edges`)에 대한 팀 동의
4. 그룹 우주 좌표를 따로 둘지
5. 별자리 선을 화면에 어떻게 표시할지(프론트 디자인)
